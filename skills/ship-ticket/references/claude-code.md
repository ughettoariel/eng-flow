# Claude Code

How the steps of `ship-ticket` and `run-epic` that depend on the harness run in Claude Code.

- **A subagent with an empty context** is a foreground headless `claude -p` call that writes its full report to `.eng-flow/reviews/`. The Agent tool of the desktop app only starts background agents, so a session that waits on them ends its turn mid-round; a foreground call keeps the turn open, so a ticket session's turn ends at a verdict note, a merge or `BLOCKED`. These calls are only for reviewers, which report and decide nothing; every decision stays in the ticket session, whose transcript keeps it. For each round, from the worktree:
  1. Run `mkdir -p .eng-flow/reviews`, create `.eng-flow/.gitignore` with `*` when it is missing, and write the diff range the step names to `.eng-flow/reviews/<head sha>.diff`. Reviewers read that file instead of running `git diff`, `git log` or `git show`, whose `--output` option writes files.
  2. Start every reviewer of the round in one Bash call, each as `claude -p "<prompt>" --model <size> --allowedTools "<tools>" > .eng-flow/reviews/<head sha>-<reviewer>.md 2> .eng-flow/reviews/<head sha>-<reviewer>.err &`, then `wait`, with the Bash timeout at its 10-minute ceiling. The prompt goes first because `--allowedTools` takes every argument after it. It carries the skill file to follow by its path in the checkout, with the instruction to read the `references/` files that skill links when it says to, the diff file, the ticket and PR numbers, and that it must not edit files or check out branches.
  3. The tools are `Read,Grep,Glob,Bash(gh pr view:*),Bash(gh pr checks:*),Bash(gh issue view:*),Bash(git notes --ref=eng-flow show:*)` and one `Bash(<command>:*)` per command of the `Checks` line of `docs/agents/project.md`. `verify-as-user` also gets one `Bash(<command>:*)` per command of the `Run` line, never a bare `Bash`. When the `Run` line names no command to start an app, as with `Run: no app`, `verify-as-user` gets the same tools as the other reviewers and nothing for `Run`.

     In a project with screens, `verify-as-user` runs in the ticket session instead of a headless call: a headless call can use only the tools its `--allowedTools` names, so it cannot drive a browser or simulator or save a capture. The ticket session follows the skill after the reviewers' `wait` returns, starts the app the way the `Run` line says, drives it with the browser or simulator tools the session has, writes its report to `.eng-flow/reviews/<head sha>-verify-as-user.md`, and saves its captures in `.eng-flow/reviews/<head sha>-captures/`, which the `.eng-flow/.gitignore` keeps out of git. The session then adds the captures to the PR description, as `file-pr` asks when screens change. The walk happens in the session's own tool calls, so its turn stays open until the note.
  4. A report without a `PASS` or `FAIL` verdict means that reviewer failed, timed out or was refused a tool: read its `.err` file and run it again.
  Read the reports from `.eng-flow/reviews/` to write the note. Name the model only when the step says which size to use: `haiku` for small, `sonnet` for large.
- **A question with options** is the AskUserQuestion tool, at most four questions per call.
- **A message to the `run-epic` session**, in the desktop app, is `SendMessage` with `to` set to the session id the handoff names; one message lists every item, each with what was found and where. In the terminal no session receives it: list the items in the final report, and the owner brings them to `run-epic`.
- **A new session for a ticket**, in the desktop app, is `start_session` with `initiation: "user_asked"`, `wake_when_done: true` so its end continues `run-epic`, `cwd` set to the worktree `run-epic` made, `use_worktree: false` so it opens that worktree instead of making another, the handoff as its `prompt`, and a `background` of at least 80 characters on why it runs. The app refuses that call on a turn that a session's report started, and on the first turn of a `run-epic` that another session started: the launch needs one message from the owner in the `run-epic` thread. In the terminal there is no such call: print the command for the owner to run in a new window, `cd <worktree> && claude "/eng-flow:ship-ticket #<number>"`.
- **How long `run-epic` stays up.** In the desktop app it stays: each ticket session that ends a turn wakes it, and it launches the next ticket that fits, after the owner's message when the launch was refused. In the terminal no session reports back, so it launches what it can, reports, and stops; the owner runs it again.
- **The agent account.** With an `Agent account` login in `docs/agents/project.md`, the session takes that account from the `env` block of `.claude/settings.local.json`, which Claude Code reads at start and keeps out of git:

  ```json
  {
    "env": {
      "GH_TOKEN": "<the agent account's token>",
      "GIT_AUTHOR_NAME": "<agent login>",
      "GIT_AUTHOR_EMAIL": "<id>+<agent login>@users.noreply.github.com",
      "GIT_COMMITTER_NAME": "<agent login>",
      "GIT_COMMITTER_EMAIL": "<id>+<agent login>@users.noreply.github.com"
    }
  }
  ```

  `GH_TOKEN` makes `gh` act as the agent account instead of the owner's login. A user-owned Project, or a repository where the agent account is a collaborator, needs a classic token with the `repo` scope, and the `project` scope when there is a board, because GitHub's fine-grained tokens reach neither. A classic token reaches every repository its account sees, so make the agent account a collaborator on this repository only, and on the Project when there is a board. When an organization owns both the repository and the Project, a fine-grained token limited to them works instead. Pushes use the token too only when git's credential helper is `gh` (`gh auth setup-git`); otherwise git pushes with the owner's credentials. The `GIT_AUTHOR_*` and `GIT_COMMITTER_*` variables sign every commit, merge commits and note commits included, as the agent; the `<id>` is `gh api users/<agent login> --jq .id`. When `git check-ignore .claude/settings.local.json` prints nothing, git would commit the token, so add `.claude/settings.local.json` to `.gitignore` and write no token until the check prints the path. The file is untracked, so a worktree `run-epic` adds starts without it: copy it in before opening the session. A session that starts without it runs as the owner, and the login check of `ship-ticket` stops it.
